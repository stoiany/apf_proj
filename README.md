## Лабораторна робота №4

Цей репозиторій містить клієнт-серверний веб-застосунок, де фронтенд взаємодіє з бекендом через REST API.

Встановіть залежності:

```bash
npm install
cd api && npm install
cd ../frontend && npm install
```

Поверніться в кореневу папку та запустіть проект:

```bash
npm run dev
```

Порти за замовчуванням:

    Frontend: http://localhost:5173

    Backend API: http://localhost:3000/api/v1

Нижче наведено кроки для перевірки ключових вимог інтеграції:
1. Перевірка GET (Завантаження списку)

   Відкрийте фронтенд у браузері.

   У таблиці спочатку з'явиться стан «Завантаження...», після чого відобразиться актуальний список чергувань з бекенду.

2. Перевірка POST (Створення запису) та Валідації

   Заповніть форму додавання чергування валідними даними та натисніть «Зберегти».

   Ви побачите повідомлення про успіх, а таблиця автоматично оновиться.

   Перевірка 400 (Bad Request): Спробуйте відправити порожню форму або неповні дані. Фронтенд покаже відповідне повідомлення.

3. Перевірка CORS

   Запит виконується з localhost:5500 на localhost:3000. Браузер успішно пропускає дані, оскільки на бекенді налаштовано жорсткий whitelist (allowedOrigins) для порту фронтенду.

4. Перевірка 500 / Network Error (Надійність клієнта)

   Вимкніть сервер (зупиніть процес у терміналі) і спробуйте оновити сторінку або додати запис на фронтенді.

   UI не «зависне», а покаже зрозумілу помилку: Помилка мережі або CORS (сервер недоступний).

5. Перевірка Timeout (AbortController)

   У клієнті налаштовано таймаут очікування запиту (10 секунд). Якщо бекенд не відповідає за цей час, запит автоматично скасовується, і користувач бачить статус 408 Request Timeout.

### Контракти (DTO) та Версійність

Для забезпечення стабільної роботи фронтенду застосовується принцип зворотної сумісності («не ламати формат»). Всі API роути мають префікс версії (наприклад, /api/v1/shifts).  

### Правила сумісності форматів обміну даними (DTO):

Заборонено видаляти або перейменовувати існуючі поля, які вже використовуються фронтендом (наприклад, зміна time на timeSlot у v1 є breaking change).  

Нові поля додаються виключно як необов'язкові (?) або з дефолтними значеннями, щоб старий клієнт міг їх ігнорувати без збоїв.  

Зміни, що ламають формат (Breaking changes), реалізуються тільки через нову версію API (наприклад, /api/v2/shifts).
